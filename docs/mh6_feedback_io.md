# 九路反馈与发送失败处理

实机运动输出仍锁定，`mh6_teleop_run.py --enable-hardware` 仍在串口与 AVP 初始化前退出。
启动位、限位、跳变阈值及电机端点仍由用户填写 `DHandControl/config/mh6_hardware.json`，没有替换任何 null。
读取反馈不会自动填写配置、对齐自然位、发送保持位置或触发启动运动。

## 可以读取什么

| 通道 | 真实查询字段 | 未提供的字段 |
|---|---|---|
| F1–F5 | 目标与当前位置、温度 °C、电流 mA、力 g、故障位、协议校验与固件状态 | 无到位保证 |
| M1–M4 | 当前位置、温度 °C、电压 mV、协议校验与固件状态 | 电流、力、故障位均为 null |

位置单位为执行器协议位置单位，不是角度度数。M4 也必须使用兼容的 Lobot 反馈协议；
当前无法在没有硬件测试的情况下确认型号与接线。返回位置允许记录真实读数，不能用目标位置代替反馈。

`FeedbackPoller` 每次只查询一路，顺序 F1..F5、M1..M4，发送与反馈由同一线程顺序执行，
驱动还使用 transaction_lock 保护完整 Modbus 事务。只使用一个进程占用同一串口。
不设置追赶队列，超时后跳过积压时隙。`--feedback-rate 10` 是九路合计 10 次查询/秒，
理想情况下每路约 1.11 Hz、一圈约 0.9 秒，绝不是每路 10 Hz。
M 系列每次状态查询会依次读位置、温度、电压，字段不是同一瞬间采集。
查询耗时可能使实际控制频率低于 `--rate`，需要台架测量后再调整轮询频率。
默认 Modbus 超时 0.15 秒，关闭 pymodbus 隐式重试，避免丢失应答后重放运动命令。

每路保存 last_attempt、last_valid、age_seconds。ID、固件状态、校验或查询失败时，
更新失败记录并保留之前的有效读数，但不刷新有效读数时间。没有成功反馈时 last_valid 为 null。
这是电机反馈的采样记录，不涉及 AVP 追踪新鲜度监测。

## 独立只读反馈入口

以下命令由操作者在确认串口后执行，程序只构造反馈驱动，没有运动发送器：

```bash
conda activate mh6
python /home/stw/DHandControl/DHandControl/scripts/mh6_feedback_read.py \
  --port /dev/ttyUSB0 \
  --feedback-rate 10 \
  --serial-timeout 0.15 \
  --duration 30 \
  --output /home/stw/DHandControl/recordings/feedback_01.jsonl
```

不指定 duration 时持续到 Ctrl+C。输出文件必须不存在；每次查询及最新反馈快照都保存到 JSONL。
这个入口不依赖人手标定、启动位或限位，因为它不会发送位置指令。
“只读”会写入桥接器的设备选择和查询命令寄存器，但只使用查询命令 0x07/0x08，不调用运动、清错或设置 ID。
结束时只关闭连接，不向机构发送停止、卸载或回零指令。

## M1–M4 的固件依赖

仓库 `DHandControl/DH6Modbus` 新增只读命令 0x08，查询后写入寄存器 72..79：

| 地址 | 含义 |
|---|---|
| 72 | 舵机 ID |
| 73 | 本次查询是否完整有效 |
| 74 | 当前实际位置（有符号 16 位） |
| 75 | 温度 °C |
| 76 | 电压 mV |
| 77 | 查询错误：0 成功，1 失败 |
| 78 | 本次三次响应均通过 ID、命令、长度和校验检查 |
| 79 | 查询序号，16 位回绕 |

固件状态 0x94 表示成功，0xF6 表示查询超时或响应无效。每次查询先清结果，失败不沿用旧位置。
UART 读取使用固定长度缓冲区和每字段 10 ms 超时，支持分段到达，拒绝错误 ID、命令、长度和校验。
旧五指查询 0x07 与寄存器 60..71 保持兼容。固件在完成查询后才应答命令寄存器写入，Python 不再额外等待 30 ms。

**这里只修改了固件源码，尚未刷写。旧桥接固件无法提供新的手掌反馈。**
主机测试已编译实际草图、舵机库和电缸库并用模拟 UART 执行协议测试；
这不替代 ESP32 工具链构建、上传和实机总线验证。

## 发送确认与失败锁定

`HardwareSender.send(packet)` 接收最终九路整数位置，不重复映射。
驱动依次写参数块、写命令、立即读回固件状态；只有状态 0x90 才认为桥接下发得到确认。
这不证明各执行器收到了数据、同步启动或已经到位。

`ActuatorIO` 规则：

1. 只有发送成功后，才提交“上一已确认指令”的九路位置和 generation；它们不是实际位置反馈。
2. False、异常或非 0x90 的固件状态均锁定故障，记录参数写入/命令写入/状态读取阶段。
   应答丢失可能意味着机构已部分运动，既不把请求值当作成功，也不假定机构完全没动。
3. 故障后阻止后续运动写入，不自动重发、重连、回零或补发保持指令；反馈继续读取。
   有效五指反馈带故障位时，同样阻止后续运动写入。
4. `reconcile_from_feedback()` 是显式恢复接口，没有自动调用者。
   必须配置完整、九路均有故障后开始采集且最近查询成功的健康反馈，位置在已填写限位内，
   且每路反馈年龄不超过两个理论轮询周期，才可重设位置参考并解除锁定。它自身不发送运动。

暂停发送不能停止已经执行中的上一条命令；主动停止及启动位衔接仍未完成。
普通遥操作主循环目前只接入无发送器的 ActuatorIO，日志中 execution 为 SIMULATED_NOT_SENT、
feedback.enabled 为 false。上述真实发送路径仅通过注入模拟设备验证，尚未开放给 CLI。

## 验证

Python 单元测试覆盖完整报文、写应答丢失、固件拒绝、失败不提交、锁定不重发、
反馈继续轮询、历史读数不刷新、故障后显式恢复以及只读入口不调用运动函数。
主机 C++ 测试覆盖实际固件的分段响应、错误 ID/命令/长度/校验、超时、结果清除及寄存器内容。
现有录制的离线回放日志继续保持可重复，Solver 与 Mapping 算法未因本次 I/O 修改而改变。
